# Подключение к Jira: формирование контекста и подготовка к игре

Jira — основной источник фактов для колоды. Цель подключения — не «оценить человека по метрикам», а
собрать **проверяемые эпизоды** за период: что человек сделал, как написал, когда и как двигал задачи.
Из эпизодов руководитель собирает досье и карты, а оценку дают оба игрока за столом.

```
Jira (read-only)  ──fetch──▶  activity.json  ──signals──▶  signals.md ─┐
                                                                         ├─▶ dossier.md ──▶ cards.json ──build──▶ game.html
Саммари встреч (POKER_DAILY_DIR)  ───────────────────────────────────────┘        (prompts/dossier.md, prompts/cards.md)
```

Всё, что ниже стрелки `fetch`, лежит в `sessions/<login>_<YYYY-MM>/` и в git не попадает.

## 1. Принципы

1. **Только чтение.** Модуль ходит в Jira исключительно `GET`; в Jira ничего не пишется — ни
   комментарии, ни поля, ни ворклоги. Итоги игры остаются у руководителя.
2. **Креды не в репозитории.** `JIRA_URL`, `JIRA_PROJECT_KEY`, `JIRA_USERNAME`, `JIRA_PASSWORD` —
   в `.env` проекта, во внешнем `.env` (`--env` / `$POKER_ENV`) или в переменных окружения. Можно
   переиспользовать `.env` основного рабочего репозитория, не копируя его.
3. **Маппинг полей — в конфиге.** Кастомные поля у каждой Jira свои: `config/jira.json`
   (шаблон — `config/jira.example.json`). Код не содержит id полей конкретной инсталляции.
4. **Бережно к серверу.** Пауза между запросами (`pause_seconds`, по умолчанию 2 с), backoff на 429.
   Никаких повторов на 4xx/5xx, кроме 429.
5. **Минимум данных.** Берём только действия самого человека за период: его комментарии, его
   переходы, его правки полей, его ворклоги. Чужие комментарии в выгрузку не попадают.
6. **Сигнал ≠ оценка.** Автоматика только подсвечивает, *где смотреть*. Каждый сигнал перед
   попаданием в карту проверяется руками по задаче и, по возможности, по встрече.

## 2. Что выгружается (`poker/fetch.py`)

**Пул задач** проекта `JIRA_PROJECT_KEY`, обновлённых в период:

| Корзина | JQL | Когда |
|---|---|---|
| `assignee_or_reporter` | `assignee = X OR reporter = X` | всегда |
| `acceptor` / `setter` / `responsible` | `cf[<id>] = X` по `role_fields` | `--roles` |
| `worklog` | `worklogAuthor = X AND worklogDate в периоде` | `--roles` |
| `commenter` | `issueFunction in commented("by X")` (ScriptRunner) | `--roles` и `scriptrunner_commented: true` |

Корзина, которую Jira не поддерживает (400), пропускается и пишется как `null` — выгрузка не падает.

**По каждой задаче** (`GET /issue/{key}?expand=changelog`) — с фильтром «автор = X и дата в периоде»:

- `comments` — текст и время его комментариев;
- `transitions` — его переходы статусов (из changelog);
- `field_changes` — его правки остальных полей (срок, исполнитель, приоритет, описание…);
- `worklogs` / `worklog_hours` — его списания времени;
- `self_set_fields` — поля-роли, которые он сам проставил на себя;
- `roles` — в каких корзинах задача нашлась.

Почему фильтр постфактум: Jira Server не умеет JQL-фильтр «комментарий/переход сделан автором X».
Поэтому берём пул задач, где человек участвует, и фильтруем историю каждой задачи локально.

## 3. Как из данных получаются сигналы (`poker/signals.py`)

| Сигнал | Правило | Масть · компетенция | Что проверить руками |
|---|---|---|---|
| `all-on-self` | исполнитель ≥60% задач и делегирует ≤1 человеку | ♥ Делегирование | выбор или трудность отпустить |
| `delegated-silent` | делегированная задача просрочена, от сотрудника ни комментария, ни перехода | ♥ Контроль делегированного | есть ли контроль после постановки задачи |
| `duedate-shifts` | сотрудник переносил срок ≥2 раз в задаче | ♣ Эскалация и блокеры | текст комментариев к переносам: что блокировало |
| `overdue` | своя задача просрочена на конец периода | ♣ Контроль сроков | честный статус или тихая просрочка |
| `tracker-post-factum` | ≥4 перехода статуса сотрудником в окне 60 мин | ♣ Трекер как инструмент | Jira по ходу или отчётность после |
| `off-hours` | ≥3 действий вне `workday` или в выходные | ♣ Нагрузка | устойчивый темп или перегруз |
| `self-set` | сотрудник проставил себя в поля-роли | ♠ Владение процессом | решение или формальность (массовый скрипт) |
| `handoff` | есть комментарии с адресными `[~login]` | ♦ Цифровой след и хендофф | норма или разовый эталон |
| `silent-tracker` | за период ни одного комментария | ♦ Цифровой след | где живёт коммуникация |

Пороги — константы в начале `signals.py`, рабочее время — `workday` в конфиге. Время берётся
так, как его отдаёт сервер Jira (в его часовом поясе).

**Чего Jira не покажет** — и это идёт в карты-вопросы, а не в карты-факты: развитие людей (1:1,
разбор «почему»), устные эскалации, работа в чатах и на встречах, причины решений. Для этого
второй источник — саммари встреч (`POKER_DAILY_DIR`): упоминания человека, его позиции и договорённости.

## 4. Подготовка к игре: от сигналов к картам

1. **Выгрузка:** `python -m poker.fetch --login X --from … --to … --roles`.
2. **Сигналы:** `python3 -m poker.signals sessions/X_YYYY-MM/activity.json` → `signals.md`.
3. **Досье** (`prompts/dossier.md`): эпизоды «дата · источник · факт · компетенция · проявил/не проявил/спорно»,
   слепые зоны, гипотеза «сильное / слабое / риск». Каждый эпизод — с ключом задачи или встречей.
4. **Карты** (`prompts/cards.md`): 10–14 карт-фактов (баланс: сильные, зоны роста, спорные) и 2–4
   карты-вопроса по слепым зонам. Факт — без оценочных слов; гипотеза — только в `marker`.
5. **Сборка:** `python3 -m poker.build sessions/X_YYYY-MM/cards.json` → `game.html`.

Проверка перед сессией: у каждой карты-факта есть источник, который можно открыть и показать за
столом; нет карт «по слухам»; сильных карт не меньше, чем карт роста.

## 5. Подключение другой Jira

1. Скопировать `config/jira.example.json` → `config/jira.json`.
2. Найти id полей: `GET {JIRA_URL}/rest/api/2/field` — эпик (`Epic Link`), поля-роли
   (приёмщик, постановщик и т.п.). Ненужные роли удалить из `role_fields`, эпик можно `null`.
3. Нет ScriptRunner — `scriptrunner_commented: false`.
4. Самоподписанный сертификат — `verify_ssl: false`.
5. Пробный прогон: `--max-issues 3`.

Jira Cloud: работает тот же REST v2, но `name` пользователей там скрыт (GDPR) — фильтрация по
автору потребует `accountId`. Сейчас модуль рассчитан на Jira Server/Data Center.
